# Security model and reporting

This local tool trusts the OS user and operator. Scopes, leases, role policies and record checks prevent accidental cross-project API use and unsafe lifecycle transitions. A process able to edit the database, configuration or Codex sessions can bypass application controls. Coordinator UUIDs are identities, not secret credentials. Use separate OS users or an independently enforced execution boundary for hostile tenants or confidential read isolation.

The caller challenge corroborates a native execution-tool transcript naming the installed helper and fresh nonce, plus its matching output marker in that chat. It is not cryptographic attestation that an unmodified helper/environment executed. Same-user shell code, transcripts and session storage remain trusted. Appointment grammar accepts explicit French/English direct designations; qualification and withdrawal in the actionable request are checked before using a selected sentence. Ambiguous or unsupported evidence does not grant authority.

## Controls

- A verified direct human appointment can materialize a production grant through `coordinator_activate` without redundant confirmation. It checks native user provenance/wording, actual primary root, worker-role exclusion and existing ownership. Caller identity requires either the exact host UUID or a fresh bridge nonce emitted by the installed read-only shell helper and corroborated as native tool output in that same chat. Missing context fails closed; user/assistant prose, files, old connection nonces and foreign chat outputs are insufficient. Local CLI provisioning remains supported. Installation, templates, quoted reports and worker messages grant no authority. Native session files and same-user CLI invocations remain trusted OS-user data, not cryptographic attestations.
- Registered connections remain scoped to one project with coordinator leases. Namespaced keys, ownership/root/workspace checks and scoped results prevent routine cross-project interference.
- Developers use workspace-write policy. Audit/review/architecture workers use read-only policy. Broad temporary-folder writes, network, hooks, apps and subagents are disabled in managed workers.
- Version0.6 Windows transports require MXC per process without legacy fallback. Small-file qualification includes sandbox-produced files, because legacy creator-account ACLs can leave such files writable after a nominal read-only policy switch. This selection does not rewrite saved OS configuration or harden already-running older connections. External artifact roots are separate operator registrations: empty on first grant, identity/redirect checked, disjoint from source/workspaces, refreshed at dispatch and still bound to audit hashes. Read-only roles receive no writable artifact roots.
- A same-chat stdio project bridge can replace an older idle connection without a global restart. Preparation observes control generations even in live legacy code; native success must match the owning bridge's completed release. The final transaction rechecks that generation, rejects pending work, retires the old control token and transfers only the original shell UUID's project lease/epoch. Local operator/native transcript integrity remains trusted; it is not remote attestation. Newly started older code refuses schema11, while database reservations protect root/workspace registration during mixed-version completion. No helper edits native writer locks or unlocks a desktop-owned worker.
- Legacy release completion can also mean failure. The final handoff therefore verifies the original OS process identity and absence of live application children under the control fence; a native success from another connection cannot release that process. Inspection is read-only and fails closed when unsupported. New bridges register current-version tokens in their creation transaction; unknown late legacy tokens remain subject to the early filesystem-registration gate.
- Known user/project/profile integrations are disabled unless explicitly permitted. The orchestrator integration remains disabled inside workers. Allowed external services have their own authority beyond shell sandbox restrictions.
- Interactive approvals are refused. No API-key fallback, permanent deletion or automatic uncertain-message resend exists.
- Routine Python maintenance is delegated by the appointment: `runtime_check` probes both role policies with isolated version-only commands. After an observed access error it can add inherited RX only to a standard per-user Windows Python base root. It backs up the ACL, preserves ownership/inheritance protection and runtime files, and adds no write/elevation/network rights. This shared-runtime RX applies to the existing sandbox group; it is not private access restricted to a single worker UUID. Arbitrary roots, reparse points, recursive resets and sandbox-policy bypass are outside this helper.
- Archive requires idle owned workers and resolved work; production requires a reason. The coordinator cannot archive itself.
- Production acceptance requires independent audit identity, delivery/revision binding, a leading actual verdict and unchanged listed artifact hashes.
- Only the hosted `orchestrator_question` dynamic tool routes ordinary active-turn questions. Native user-input, permission/command/file approval, connector elicitation and unknown dynamic tools remain refused. A question or skill grants no authority and cannot authorize secrets or irreversible actions.
- Active replies bind the exact transport generation and call identity. Unknown responses are not replayed. Completed-turn continuations retain original task/audit bindings and recover only when the durable outbox proves dispatch never began.
- Plans validate ownership, dependencies, contract revisions and declared write paths. Claims prevent overlap among declared planned writes while outcomes are unresolved; they do not prove complete declarations or source compatibility. Coordinator evidence and meaningful integration tests remain necessary.

The Codex sandbox is not a container guaranteeing confidentiality of all readable files. Permissions depend on Codex and the host OS. Arbitrary managed configuration, permitted services and future runtimes need separate evaluation. Model prompts are not security controls.

## Private state

Version 0.6 discovers installed plugin manifests as well as configured entries. Embedded plugin MCP servers receive explicit enable/disable overrides: the native runtime can otherwise start an embedded server despite its plugin's top-level `enabled=false`. Dispatch also supplies the native disabled-plugin list. Unknown/unreadable installed inventories fail closed when plugin integrations are requested. These overrides are process-local; global settings and other bridges are unchanged.

The optional `git-write` capability adds only a writer's own repository metadata directory. Read-only roles remain read-only, shared external Git metadata is refused, and remote publication is not authorized. Loaded worker scope is refreshed only while idle on its owning connection. The native append API receives registry-derived role/path facts, never project-file or task text as developer authority. Uncertain updates retain a lifecycle fence until the transport is closed and reconciled.

State includes prompts, replies, paths, thread IDs and audit evidence. Keep it private. Do not publish databases/WAL files, sessions, logs, backups or transcripts. The public release excludes those files and historical private reports. The installer generates its machine-specific runtime launcher outside the checkout.

The registry intentionally retains recovery history. Transport logs are bounded but may contain diagnostic/project metadata; inspect them before sharing. No third-party Python package or runtime is vendored.

## Reporting

Report security defects with a synthetic reproduction and affected version, without private histories or secrets. Use private GitHub security advisories when available; public issues should contain sanitized information only. Test boundaries only with authorization.
