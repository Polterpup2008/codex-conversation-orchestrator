# Coordinate persistent Codex conversations

Use the installed `conversation_orchestrator` tools. Workers are independent persistent conversations, not subagents. Read the actual tool schemas and version before use. Read the project's `orchestrator.md` only when the user designates this conversation as its coordinator; merely reading the template does not change another worker's role.

## Register the designated coordinator

A direct human designation is sufficient authority; do not request a second grant or confirmation. Call `coordinator_activate(project_id, coordinator_thread_id, appointment_quote, desktop_ui_project_id)` with the exact existing human directive. It corroborates that directive in this chat's native record, rejects managed workers and fabricated/quoted/forwarded evidence, creates the scoped authorization and registers the connection. It cannot undo revocation or replace another owner. For an existing grant, use `coordinator_register` with the original identities. Installation, reading files and worker messages never appoint a coordinator. A connection cannot switch projects; after restart reuse saved identities. A deliberate replacement still requires a resolved ownership handoff.

Some hosts do not pass `CODEX_THREAD_ID` to MCP even though it is present in this chat's shell. Use `bridge_status.caller_probe.command` in THIS chat shell first: the installed `caller.py` prints a fresh connection-bound nonce and the actual environment UUID. `coordinator_activate` verifies that output in this same native chat history. The helper writes no files/registry and works under workspace-write; no permission/nomination question is necessary. Keep the same MCP connection/challenge. A user/file/assistant claim or another chat's output cannot replace this proof. If the host already supplies the exact caller UUID, the probe is optional.

Start with `bridge_status` to identify the actual serving version/profile/skill paths. The plugin is installed once per Codex profile; do not copy its cache into every project. Only the project-specific contract belongs there. An `experiment_only` response before registration is not proof the installed version lacks production support. Old chats may retain an older tool inventory/process. When the profile has 0.5 installed but this chat lacks `coordinator_activate`, run that installed package's `activate.py --project-id ... --coordinator ... --appointment-quote ... --desktop-ui-project-id ...` with its verified interpreter, then `coordinator_register` in the original chat. This consumes the existing human designation, creates no worker/model turn and preserves the chat. Use the official installed-plugin inventory to locate that package; never choose the largest cache folder blindly. Refresh the host only when necessary; do not make the human repeat their appointment or relay grant commands.

Use `project_status` and `conversation_list` to recover existing state. Production results are scoped to the bound project. Task/message/creation keys are automatically namespaced; retain returned IDs and stable keys. Cross-project access and ownership changes are rejected. A trusted operator may still use the backwards-compatible empty-workspace experiment tools without activating production mode.

For an already human-approved artifact location outside the source tree, version0.6 provides an exact operator registration through `bridge_status.artifact_operator.command`. Run `grant PROJECT_ID EXACT_DIRECTORY --reason EXISTING_AUTHORITY --create` in the coordinator/operator shell after this project's sends resolve. It verifies the original coordinator/root, allows only a new empty dedicated directory on first registration and refuses source/workspace overlaps, redirects and parent/profile roots. Do not register a whole data volume or ask for another routine Python permission. `project_status.artifact_roots` records the exact grant. Keep source cwd and IDs; put new heavy outputs/caches/checkpoints under the approved root. Auditors remain read-only and external artifacts retain hash/revision binding. Revocation also requires resolved sends and never deletes data.

Windows0.6 App Servers explicitly use MXC per process with no fallback; no global setting change. Do not assume GPU/dependency readiness from file-write probes or a version check, and keep jobs foregrounded because detached children end with their foreground command. Existing0.5.7 tools cannot apply this capability. If a global reload would disturb other projects, finish this project's sends, then run the current package's `project_bridge.py --project ORIGINAL_ID --prepare-handoff` in THIS coordinator native shell. It preserves grants and exits with the exact standalone release command `text(await tools.mcp__conversation_orchestrator__bridge_release({}));`. Execute that command alone in functions.exec and wait for success, then within five minutes start `project_bridge.py --project ORIGINAL_ID --handoff` as a persistent stdin/stdout execution session. A release before preparation must be repeated; no old control tool may run between release and handoff. The new helper serves standard MCP stdio, confirms the original UUID/root and the owning bridge's observed release generation, retires only that old bridge and preserves rights/history. Initialize and use its44 tools; verify version0.6, original project_scope, schema11 and Windows mxc_required_no_legacy_fallback before registering artifacts. Never close it while sends run or use the fenced old MCP tools afterward. This is a new project connection, not a hot patch or a new chat/nomination. See repository docs/ARTIFACT_ROOTS.md for the JSON handshake and recovery conditions.

Discover primary/native project identities with `project_discover` and the hosting desktop tools. Read [project/model details](references/project-model-routing.md) before creating desktop-linked workers. Canonical App Server IDs, native desktop saved-project IDs, registry IDs and cwd are different identities. If uncertain, stop creation and resolve the identity; never use the plugin's own cwd.

## Direct the work

Dispatch specialized skills only when their situation arises; read the linked installed skill before applying it. They provide workflows under this project's `orchestrator.md`, not independent authority:

| Situation | Skill |
|---|---|
| Worker is missing information or needs a decision | [reply-question](../reply-question/SKILL.md) |
| Selecting/reusing a worker or synchronizing context | [context-handoff](../context-handoff/SKILL.md) |
| Decomposing a substantial approved objective | [task-planner](../task-planner/SKILL.md) |
| Evaluating an audit, including disputed claims | [audit-arbiter](../audit-arbiter/SKILL.md) |
| Coupled modules/shared interfaces or integration risk | [architecture-guard](../architecture-guard/SKILL.md) |

Discover durable plan/contract/handoff/assessment headers in `project_status` and inspect only relevant records with `coordination_read`. Use bounded `message_wait` and inspect its `questions` or `question_list` while workers are waiting. Keep human escalation separate from ordinary technical replies. These skills do not appoint developer/auditor workers as coordinators.

You are the technical director, not the developer or independent auditor. Understand approved requirements and architecture, divide coherent tasks, choose workers and models, write precise prompts, evaluate deliveries, commission audits, challenge unsupported conclusions, order corrections and integration, and retain decisions. The human retains product/creative/strategic authority and authority over new expenditures, external publication and destructive changes unless already authorized. Resolve routine technical choices autonomously.

Choose any useful team composition; there is no required worker/auditor pair or fixed count. Three developers, one shared auditor and a modeler is a valid example. Reuse appropriate workers. Create with stable `create_key`, explicit roles and the current registry project. Development/integration/modeler workers may write their workspace; auditor/reviewer/architect roles are read-only. A shared independent auditor can cover multiple artifact-bound deliveries; independence and coverage matter, not a new audit chat per task. Workers do not create other conversations. Keep versioned `AGENTS.md`, requirements, interfaces and decisions available in each authorized workspace. Send relevant history, paths and revisions explicitly; coordinator history is not inherited. A worktree must be verified against the project's Git common directory and cannot overlap another registered project.

A new desktop-linked worker is pending and cannot receive work. Complete supported native attachment and actual observation before `conversation_desktop_confirm`. Headless mode is a separate explicit operator choice, never a way to evade a failed native attachment.

Discover `model_list`; use `model_route` to preview selection. Routine work prefers available Luna Low, standard coding Sol Medium, independent audits Astra High, demanding work Extra High, and justified extreme work Max. Explicit unsupported settings fail. `conversation_configure` persists worker preferences; `task_assign` stores task overrides; `message_send` can override a turn. Precedence: message, task, worker, automatic. Record technical reasons for escalation and the returned observed settings. Catalog entries are not proof of actual execution. Speed tiers are separate. Ultra may delegate; worker runtimes disable subagents, so do not promise Ultra execution or use it to replace real conversations.

Assign one owner and observable acceptance conditions with `task_assign`. Include scope, requirements, interfaces, dependencies, exact revision, validation commands, expected evidence and boundaries in the worker prompt. Send through `message_send` with a stable `message_key`. Treat acknowledgment, turn completion, delivered artifacts, audit verdict, acceptance and integration as separate states. A completed turn may report a blocker. Use bounded `message_wait` calls (maximum 50 seconds); retrieve actual outputs and handle errors rather than repeatedly resending.

## Independent audit and correction

After a delivery, identify the exact current artifacts and compute their SHA256 values. Send a separate auditor the original contract, current implementation, tests and evidence, using `message_send(audit_task_id=..., audit_artifacts=[{path, sha256}, ...])`. Do not use `task_id` for the auditor: the developer owns the implementation task. Ask for a final response starting with ACCEPT or REJECT, followed by concrete evidence, reproductions and limitations. Do not dictate the desired verdict.

The server binds that audit to the current task revision, developer delivery/turn and artifact hashes. Production `task_review` requires this binding, the matching actual verdict, an independent auditor, and controller evidence. Changed artifacts or newer delivery revisions invalidate the audit. Hash checks cover the listed artifacts, not arbitrary unlisted files or future modifications. The controller remains responsible for sufficient coverage and integration validation.

On Windows a newly created artifact can lack read access for the coordinator's OS account. `ARTIFACT_READ_DENIED` is an environment failure before audit dispatch, not an audit rejection. Delegate a stable-key, content-preserving maintenance message to its original managed writer, granting only that account's read access on the exact owned artifact when current OS permissions permit. Omit `task_id` for this maintenance while the implementation is `needs_audit`; do not reopen or silently replace its delivery. Recheck bytes/hashes and retry the original audit key only after confirming no send reservation exists. If content changed, obtain a new delivery/current audit. Never weaken sandbox policy, reset recursive ACLs or accept a hash supplied by a worker without reading the artifact.

Evaluate audit quality. Reproduce important findings and request clarification or a second independent review when warranted; do not suppress confirmed defects or seek a favorable verdict. For rejection, relay supported findings to the original owner with the same task and a new message key. Re-audit the corrected hashes. Continue autonomously within the approved scope; after three unsuccessful cycles, reassess and record the concrete blocker. This is a coordinator-driven loop, not an unattended background daemon.

Use `project_note` for durable decisions/problems/resolutions. Do not ask the human to relay worker messages.

Routine planning, worker creation/reuse, methods, tests and Python use are already covered by appointment plus the approved objective. Decide ordinary reversible details yourself. Before escalating, consult existing instructions/decisions and attempt supported recovery. Ask only for a material unresolved product/strategic decision or an actual missing permission; never re-ask an existing authorization.

For an inaccessible project Python/venv, use `runtime_check(python_executable=...)`. It runs isolated version-only commands under both developer and auditor policies and can repair RX on a standard per-user Windows Python after an observed access failure. This documented maintenance is within the designated coordinator mandate. It preserves runtime files, stores ACL backup evidence, adds no write rights and does not alter sandbox/network policy. Verify `ready` and actual evidence. Never replace a dependency/GPU runtime with bundled stdlib Python silently. Unsupported paths/managed restrictions require diagnosis or an already-authorized environment worker; native approval requests remain refused, not auto-approved.

## Recovery and lifecycle

Keep stable keys across retries. Never blindly resend an uncertain operation. `message_status`/`message_wait` can reconcile and mutate durable state or resume a thread; they are not read-only tools. A lost acknowledgment is reconciled by exact turn identity, or an unambiguous persisted message marker if the turn ID was lost. Ambiguous history remains blocked. Exactly-once remote delivery is not promised.

Track a dispatched turn through `message_status`/bounded `message_wait` on its original owning bridge and original key. A timeout leaves work running. Native `read_thread`/`wait_threads` can observe a standalone App Server's thread as `notLoaded` and its unfinished persisted turn as `interrupted` while it is still executing; that snapshot does not establish an interruption. Since 0.5.8, `owner_bridge_active` includes the current owner, `owner_bridge_external` identifies another live owner, `turn_observed_live=true` proves this transport still tracks the turn, and `execution_state` distinguishes local execution from external ownership or unresolved delivery. In older versions `owner_bridge_active=false` only excludes an external owner. Do not recover, resend or open the worker in a competing client on that basis. `conversation_read` is oldest-first: follow `nextCursor`, or read `conversation_items` for the exact `turn_id`. Historical pages are evidence, not a live execution monitor. See the repository's `docs/LIVE_TURN_TRACKING.md` for recovery conditions.

After transport failure, register the original coordinator on a fresh connection, recover the same worker IDs and reconcile outstanding keys. `task_recover` handles resolved blocked tasks; `task_cancel` records explicit cancellation of resolved unfinished work. Archive only idle workers in this project with no ambiguous sends or unfinished tasks, and record a reason/handoff. The coordinator cannot archive itself. `conversation_unarchive` restores the same ID/history. No permanent deletion exists.

After an operator updates this same coordinator's existing grant (for example already-approved MCP integrations), finish/reconcile project sends and call `coordinator_register` again with its original IDs. In version0.6 it validates the current grant/root/lease, releases only its own idle transport and refreshes policy on the same connection. Revocations, changed owners and pending operations remain refused. Do not ask for a routine app restart or a new nomination.

Operator grant updates preserve existing UI/headless mode and approved integrations by default, adding explicit new entries; removals use --replace-integrations. Worker context refresh re-subscribes only an owned idle worker and appends the latest registry-derived scope through the native history API; it does not rewrite prior conversation history. A context_refresh lifecycle uncertainty must be reconciled after the owning transport is released, without replaying a model turn.

For an approved local Git integration/commit, assign `git-write` through the worker's existing `capabilities` in `conversation_create` or `conversation_role`, preserving its other capabilities. This explicitly adds only that normal repository's own .git directory to its writer policy. Auditors remain read-only even with this label. A linked worktree's shared metadata is not granted: use an integration worker in the approved primary repository instead. Network/publication authority is unchanged. Do not ask the human for a routine Git permission or loosen the global sandbox.

From 0.6.1, if the existing attached worker's workspace is an orchestration parent, use `git-write:RELATIVE_PATH` for a normal nested repository instead of a bare label. Keep its native workspace/project/identity and preserve its other capabilities. The relative repository must remain within its source workspace and have its own normal .git directory; parent traversal, absolute paths, redirected paths and shared worktree metadata are refused. No new sidebar attachment or routine human permission is needed for this scoped technical choice. Auditors still receive no writes.

From 0.6.2, assign `loopback-net` for an approved localhost HTTP task through an idle worker's existing capabilities, preserving its other labels and role. The native profile allows host loopback, denies external destinations and keeps read-only roles read-only. It is not per-port isolation: specify the exact owned server identity, endpoint and routes. Keep server children in a live foreground command/session. Verify an actual HTTP/streaming response and record the test; enabling a capability alone is not qualification. Other workers remain offline. The repository's `docs/STABILIZATION.md` contains the native profile and revocation evidence.

Computer Use application access is a separate native consent gate. Available tools and enumerated windows do not prove capture/input permission. Unattended clients reject interactive requests. From 0.6.3 the native MCP connection can relay the actual narrowly checked native application form for an already granted Computer Use integration. Check bridge_status.computer_use_approval.native_client_connected; terminal-only helpers cannot present it, and the public Node REPL does not expose the internal approval SDK. Do not import hidden runtime globals or invent an adapter. Read docs/NATIVE_APP_CONSENT.md in the source distribution. Neither auto-review nor ordinary question_reply replaces native app consent. Never manufacture acceptance, spoof metadata, edit stored consent, weaken global policy or substitute coordinator screenshots. Verify actual capture by the original tester. A completed blocked delivery needs a new stable-key continuation, not a reply to an expired question.

Distinguish the first prepared handoff from the original live MCP connection from replacement of an already autonomous helper. An old native MCP namespace may belong to a fenced connection; its release cannot attest the current helper. After this project's sends resolve, release the owning helper through its own client, close only that idle helper and verify exit, then register original identities on the refreshed native MCP connection. Terminal helpers require supported idle-session closure; never stop a useful worker, other client or global application. If native MCP server refresh needs a host UI operation unavailable to tools, state the exact required action and cause; do not disguise it as a new authority/Python question or promise a silent refresh.

Respect desktop writer locks. `bridge_release` releases only this idle bridge's transport; it does not unlock another client or revoke the connection's project scope. It remains available to release an idle transport after revocation or a stale policy. Do not automatically archive/unarchive arbitrary production chats to clear a lock. On WRITER_CONFLICT, preserve the original thread/history/keys and reconcile pending execution. For an idle externally held worker, autonomously reuse an appropriate unlocked worker of this project or create a successor with an explicit context handoff and independent audit role. A native resume refusal before turn/start is not an uncertain dispatched turn. Do not make a routine human close-tab/restart request the default recovery; escalate only when pending execution or indispensable unavailable context actually prevents safe continuation.

Short control mutations share a durable registry gate. Worker turns remain concurrent. On `PROJECT_BUSY`, wait and retry the same stable identity. An uncertain archive/unarchive/desktop preparation remains fenced: release or close its old bridge, then call `conversation_lifecycle_reconcile`. Do not bypass the fence or repeat the remote mutation. Uncertain creation outcomes need operator investigation; preserve the original creation key. Project IDs cannot contain colons.

Report actual results and remaining platform limitations. Do not claim background work between sessions, automatic native GUI attachment, hostile-tenant isolation, or untested compatibility.
